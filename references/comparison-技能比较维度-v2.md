# 技能比较维度 v2

先确认用户指定的各仓库及技能入口，再使用下表取证。多个仓库沿用同一组相关维度；无需每次展开所有维度。不作默认选型推荐或融合设计。

| 维度 | 需要回答的问题 | 主要材料 |
|---|---|---|
| 定位与触发 | 解决什么问题？哪些请求会触发？范围是否过宽？ | frontmatter、UI 元数据 |
| 输入前提 | 需要哪些地址、文件、凭证或上下文？缺失时如何处理？ | SKILL.md、参数解析 |
| 执行流程 | 给出原则还是可操作流程？何时分支、停止、重试？ | 主规则、引用文档、脚本 |
| 修改范围 | 是局部修改还是全局重构？不同入口是否一致？ | 全版、精简提示词、默认提示词 |
| 事实边界 | 如何保留事实、必要条件和不确定性？如何处理不利结果？ | 明确规则、实际示例 |
| 工具与依赖 | 哪些环节由脚本实现？调用什么服务？哪些依赖只用于安装或验证？ | scripts、依赖清单、配置 |
| 输出交付 | 交付正文、报告、文件还是外部应用修改？是否有可追溯来源？ | 输出规范、实现 |
| 示例一致性 | 改写是否新增无依据的数字、机制或因果？是否违背核心规则？ | 原始输入、输出示例、声明 |
| 测试证据 | 测试验证安装、格式、功能还是效果？有没有实际运行证据？ | tests、CI、运行日志 |
| 分发与版本 | 是单文件 Skill、插件或组合包？镜像与语言版本如何组织？ | 目录、manifest、构建脚本 |

判断的粒度须与证据相配。例如，静态源码可证明“实现了下载失败时保留旧文件的分支”，不能自动证明所有异常情况下都可靠。CI 配置可证明“安排了该测试”，不能证明某个提交已通过。

发现缺失时说明查阅范围，例如“选定目录及其引用文档中未找到事实保留规则”。只有完成必要追踪后，才作较广的缺失判断。不要因某入口短小就推定功能弱，也不要因引用文件多就推定设计成熟。

比较不同版本或同源派生项目时，只陈述能从提交、署名、许可证和内容中证实的关系。相似文本本身不能证明抄袭或派生历史。

若用户要求实测，使用用户提供或可核实的真实任务材料，保持输入、工具权限、模型条件和评价口径一致；报告实际设置及局限。没有真实输入时先交付规则比较，不补造基准样本。
